Linking is the step you take the day a non-engineer needs to manage access. It adds a hosted dashboard and an approvals inbox without touching anything about how your application runs. Your Application remains the org root, the sole writer, and the only thing on your request path. The only thing that changes is that Alfiz Cloud can now authenticate dashboard sessions and relay administrative operations back to your Application for enforcement.

## What linking means

When you link, Alfiz Cloud records the association and begins brokering dashboard sessions. It does not receive a copy of your authorization data, become a writer, or sit between your application and any runtime check.

The only data that flows to Alfiz Cloud is the **opt-in audit stream**: an append-only history of writes to your Application's organizational-domain data. That stream is never evaluated — it is retained for compliance and inspection, not for making access decisions. Your Application continues to own every decision.

<Note>
  A linked Application is architecturally still standalone. The Application is the org root and the sole writer. The Service records the link, authenticates dashboard sessions, and relays contract operations — it never writes your data directly.
</Note>

## What linking does not do

It is worth being explicit about what does not change when you link:

- **No authority moves.** Your Application remains the org root. Every write to organizational-domain data — groups, roles, global grants, the reporting hierarchy — passes through your Application's enforcement. The relay forwards; it never originates.
- **No federated topology.** Linking is not federation. No catalog is published to a registry, no org-root read model syncs down, no upstream is acquired.
- **No impact on the request path.** Runtime checks remain fully in-process. `can()`, `canAny()`, and `can.fresh()` still run against your catalog, your grant rows, and your ancestry resolver — exactly as they did before you linked.
- **Unlinking is clean.** Because no authority ever moved, unlinking deletes only the link registration and relay state at Alfiz Cloud. No snapshot, no handoff, no residual state. Your Application continues running exactly as it did before.

## Runtime checks are unaffected

This is worth stating again plainly: nothing about your request path changes when you link.

```ts
// Before linking — runs in-process:
await alfiz.can({ userId }, "docs.files.read", "docs.doc:123");

// After linking — still runs in-process, identically:
await alfiz.can({ userId }, "docs.files.read", "docs.doc:123");
```

The Alfiz Cloud Service cannot observe your runtime checks in any topology. Per-check pricing is impossible by construction, and that is a guarantee, not a policy.

## How to link

Linking is a registration step — you associate your Application with an Alfiz Cloud organization and configure the relay. The `ApplicationOptions` shape does not change; `orgRoot` stays `true` (or its default).

<Steps>
  <Step title="Create an Alfiz Cloud account">
    Register your organization at [alfiz.dev](https://alfiz.dev). No payment method is required to link — billing begins when admin seats are used.
  </Step>

  <Step title="Register your Application">
    From the Diwan dashboard, create a linked application entry and copy your relay credentials. These authenticate your Application's relay channel to Alfiz Cloud — they are not used for runtime checks.
  </Step>

  <Step title="Configure the relay in your Application">
    Pass your relay credentials when constructing the Application. Everything else remains identical to your standalone setup.

    ```ts src/authz/app.ts
    import { createApplication } from "@alfiz-auth/application";
    import { catalog } from "./catalog";
    import { db } from "../db";

    export const app = createApplication({
      catalog,
      storage: prismaDriver(db),
      ancestry: parentPointerResolver((scope) => db.parentOf(scope)),
      orgRoot: true, // still the org root — this does not change
      // relay: { ... }  ← relay config goes here (see the Cloud setup guide)
    });
    ```

    <Tip>
      Your `alfiz` client instance (`createAlfizClient`) does not change at all. The relay is an Application-layer concern; the Client is unaware of it.
    </Tip>
  </Step>

  <Step title="Invite admin seats">
    From the Diwan dashboard, invite non-engineer administrators. They authenticate through Alfiz Cloud, and their operations are relayed to your Application for enforcement. Seat billing begins when they first authenticate.
  </Step>
</Steps>

## Replacing the hosted dashboard

The hosted dashboard is convenience, not capability. Every workflow it exposes is buildable from the headless admin kit included in `@alfiz-auth/core` — the hosted product is assembled from the same components, speaking the same provider contract.

If you outgrow the hosted dashboard or need a custom look, build your own admin UI from the kit. The `Application` you already have is its provider. Unlinking your Alfiz Cloud registration removes the relay and the hosted access — nothing else changes.

## Next: federation
