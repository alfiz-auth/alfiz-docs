The storage seam is the single interface a database must satisfy to host an Alfiz Application. All application semantics — graph integrity, request workflows, org-root gating, the audit log — live above the seam in the Application layer and are identical regardless of which driver you use. Drivers store and retrieve; they never interpret. All IDs are assigned by the Application.

## The `StorageDriver` interface

```ts
import type { StorageDriver } from "@alfiz/application";
```

A `StorageDriver` is a flat bundle of async methods organized into eight areas:

| Area | Methods |
|---|---|
| **Grants** | `insertGrant`, `deleteGrant`, `listGrants`, `countGrants` |
| **Revokes** | `insertRevoke`, `deleteRevoke`, `listRevokes` |
| **Roles** | `upsertRole`, `getRole`, `listRoles`, `deleteRole` |
| **Groups** | `upsertGroup`, `getGroup`, `listGroups`, `deleteGroup` |
| **Users** | `getUser`, `upsertUser`, `deleteUser`, `listUsers`, `listUsersInGroup` |
| **Requests** | `insertRequest`, `updateRequest`, `getRequest`, `listRequests` |
| **Catalog** | `putCatalog`, `getCatalog` |
| **Audit** | `appendAudit`, `listAudit` |

One additional method, `runExclusive(key, fn)`, serializes graph writes per key to prevent concurrent insertions from jointly forming a group or reporting cycle. Implement it with a SQL advisory lock in multi-node deployments (see [Multi-node note](#multi-node-deployments)).

### Optional methods

The following methods are optional. Custom drivers can omit them and keep compiling — the Application either falls back to a slower path or fails loudly at construction if the feature depending on them is turned on.

| Method | Enables | Falls back to |
|---|---|---|
| `getRoles(ids)` | Batched role fetch on the closure-supply path — one call per miss instead of one per referenced role | Parallel `getRole` per id |
| `appendEvents`, `headSeq`, `eventsSince`, `pruneEvents` | The Application's `events: { persist: true }` option — a persisted invalidation log for cross-process cache revalidation | Construction throws when `events.persist` is on without them |
| `putImports`, `getImports` | `publishImports` / `getPublishedImports`, and the drift report that names roles still referencing a tombstoned key | `capabilities().imports` reports `false`; the methods are absent |
| `recordMetrics`, `readMetrics`, `pruneMetrics` | The Application's `metrics: {}` option — stored usage counters and the revocation safeguard | Construction throws when `metrics` is on without them |

`memoryDriver` implements all ten. `prismaDriver` includes each group only when the corresponding delegate is present on the client you hand it — so if you merged only the ten core models and generated your client, `events: { persist: true }` and `metrics: {}` will still throw at construction. Add the [optional models](#optional-models), migrate, and regenerate first. `mongoDriver` ships the event log built in (no schema step) but does not implement the optional metrics or catalog-history methods — see [mongoDriver](#mongodriver) below.

## `memoryDriver()`

The in-memory driver is the reference implementation of the storage seam. It is complete and correct — every Application feature works with it — making it the natural choice for unit tests, local development, and ephemeral deployments.

```ts
import { memoryDriver } from "@alfiz/application";
```

```ts
import { createApplication, memoryDriver } from "@alfiz/application";

const app = createApplication({
  catalog,
  storage: memoryDriver(),
});
```

Each call to `memoryDriver()` returns an independent, empty store. Two calls produce two isolated stores — useful for testing multi-tenant scenarios or provider federation in-process.

<Warning>
  The memory driver is not persistent. Everything is lost when the process exits. Use it for tests and local dev only; use `prismaDriver` (or a custom driver) for anything you need to survive a restart.
</Warning>

### Testing with the memory driver

```ts
import { describe, it, expect, beforeEach } from "vitest";
import { createApplication, memoryDriver } from "@alfiz/application";
import { createAlfizClient } from "@alfiz/core";
import { catalog } from "./alfiz.js";

describe("document access", () => {
  let app: ReturnType<typeof createApplication>;
  let alfiz: ReturnType<typeof createAlfizClient<typeof catalog>>;

  beforeEach(() => {
    // Fresh isolated store per test — no teardown needed.
    app = createApplication({ catalog, storage: memoryDriver() });
    alfiz = createAlfizClient({ catalog, provider: app });
  });

  it("denies before any grant", async () => {
    const result = await alfiz.can({ userId: "u1" }, "docs.files.read");
    expect(result).toBe(false);
  });

  it("allows after a grant", async () => {
    await app.createGrant({
      subject: "user:u1",
      pattern: "docs.files.read",
      provenance: { kind: "admin", actorUserId: "root" },
    });
    const result = await alfiz.can({ userId: "u1" }, "docs.files.read");
    expect(result).toBe(true);
  });
});
```

## `prismaDriver`

The Prisma driver is the production driver shipped in `@alfiz/prisma`. It maps the `StorageDriver` interface onto a generated Prisma client without taking `@prisma/client` as a hard dependency — it operates against a structural delegate interface instead.

### Installation

```bash
npm install @alfiz/prisma
```

`@prisma/client` must be in your own dependencies and generated from a schema that includes the Alfiz models. `@alfiz/prisma` does not depend on it directly.

### Creating a Prisma driver

```ts
import { prismaDriver } from "@alfiz/prisma";
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

const storage = prismaDriver(prisma);
```

Pass the `PrismaClient` instance directly. Any Prisma client generated from a schema containing the Alfiz models satisfies the `AlfizPrismaDelegates` interface structurally — no cast required.

### `PrismaDriverOptions`

`prismaDriver` accepts an optional second argument:

<ParamField body="lock" type="<T>(key: string, fn: () => Promise<T>) => Promise<T>" optional>
  A cross-node serialization function for graph writes. In a single-process deployment the default in-process promise-chain mutex is sufficient. In a **multi-node deployment** you must provide a database advisory lock here so concurrent graph writes on different nodes cannot jointly form a cycle. Example for Postgres:

  ```ts
  const storage = prismaDriver(prisma, {
    lock: async (key, fn) => {
      return prisma.$transaction(async (tx) => {
        await tx.$executeRaw`SELECT pg_advisory_xact_lock(hashtext(${key}))`;
        return fn();
      });
    },
  });
  ```
</ParamField>

### The delegate interface

`prismaDriver` requires only the subset of the generated Prisma client it actually calls, expressed as the `AlfizPrismaDelegates` interface. Ten delegate properties are required and map directly to the core Alfiz schema models; four more are **optional**, and a client generated without them still satisfies the interface:

```ts
interface AlfizPrismaDelegates {
  alfizGrant: AlfizGrantDelegate;
  alfizRevoke: AlfizRevokeDelegate;
  alfizRole: AlfizRoleDelegate;
  alfizGroup: AlfizGroupDelegate;
  alfizGroupParent: AlfizGroupParentDelegate;
  alfizUser: AlfizUserDelegate;
  alfizMembership: AlfizMembershipDelegate;
  alfizRequest: AlfizRequestDelegate;
  alfizCatalog: AlfizCatalogDelegate;
  alfizAudit: AlfizAuditDelegate;

  // Optional — omit the model and the driver omits the matching methods.
  alfizImports?: AlfizImportsDelegate;
  alfizEpoch?: AlfizEpochDelegate;
  alfizEvent?: AlfizEventDelegate;
  alfizMetric?: AlfizMetricDelegate;
}
```

A generated `PrismaClient` for a schema containing the Alfiz models satisfies this interface automatically. You can also pass a hand-rolled mock for testing:

```ts
import type { AlfizPrismaDelegates } from "@alfiz/prisma";

const mockDb: AlfizPrismaDelegates = {
  alfizGrant: { /* ... */ },
  // ...
};

const storage = prismaDriver(mockDb);
```

### Schema fragment

Add the following models to your `schema.prisma`. These are a fragment — they have no `datasource` or `generator` blocks and inherit yours. All models are prefixed `Alfiz` to avoid colliding with your own models.

```prisma
/// The atomic grant tuple: (subject, role-or-pattern, scope, expiry?).
model AlfizGrant {
  id         String  @id
  subject    String
  roleId     String?
  pattern    String?
  scope      String
  expiresAt  BigInt?
  provenance Json
  createdAt  BigInt

  @@index([subject])
  @@index([scope])
  @@index([roleId])
}

/// Personal revoke — the single negative layer; only users hold revokes.
model AlfizRevoke {
  id         String @id
  userId     String
  pattern    String
  scope      String
  provenance Json
  createdAt  BigInt

  @@index([userId])
  @@index([scope])
}

/// A named bundle of permission patterns, plus its requestability policy.
model AlfizRole {
  id          String  @id
  name        String
  description String?
  patterns    Json
  requestable Json?
}

/// A user group node; its parent edges live in AlfizGroupParent.
model AlfizGroup {
  id          String  @id
  name        String
  description String?
  virtual     Boolean @default(false)
}

/// Group parentage edges (the group DAG).
model AlfizGroupParent {
  childId  String
  parentId String

  @@id([childId, parentId])
  @@index([parentId])
}

/// The authorization-relevant user record; identity stays in the IdP.
model AlfizUser {
  userId        String  @id
  active        Boolean
  orgIds        Json
  managerUserId String?
}

/// Explicit user → group membership edges.
model AlfizMembership {
  userId  String
  groupId String

  @@id([userId, groupId])
  @@index([groupId])
}

/// An access request with workflow state and snapshotted approval policy.
model AlfizRequest {
  id                String  @id
  requesterUserId   String
  roleId            String?
  pattern           String?
  scope             String
  proposedExpiresAt BigInt?
  justification     Json
  state             String
  stageIndex        Int
  stages            Json
  decisions         Json
  createdAt         BigInt
  decidedAt         BigInt?

  @@index([state])
  @@index([requesterUserId])
}

/// The published catalog — a versioned singleton (always id = 1).
model AlfizCatalog {
  id       Int  @id @default(1)
  version  Int
  document Json
}

/// Append-only audit log, ordered by `at` (epoch ms).
model AlfizAudit {
  id     String @id
  at     BigInt
  actor  String
  action String
  target String
  detail Json?

  @@index([target])
}
```

<Note>
  Timestamps (`createdAt`, `expiresAt`, `at`, etc.) are stored as `BigInt` (epoch milliseconds) for lossless round-tripping with the core types' `number` fields. IDs are opaque strings assigned by the Application — no `autoincrement` or `cuid()` is used. No Prisma relations or cascades are declared; referential integrity between Alfiz rows is enforced by the Application layer above the seam.
</Note>

### Optional models

Four more models are additive. Leave them out and everything above still works; add one when you turn on the feature that needs it. Each corresponds to an optional delegate, and **the Application refuses loudly at construction** rather than silently degrading when you enable a feature whose model is missing.

| Model | Enables | Without it |
|---|---|---|
| `AlfizImports` | `publishImports` / `getPublishedImports` | `capabilities().imports` is `false`; the import methods are absent |
| `AlfizEpoch` + `AlfizEvent` | Event persistence (the 0.7.0 default) and so client revalidation | Persistence silently stays off under the auto default; an explicit `events: { persist: true }` **throws** |
| `AlfizCatalogVersion` | Catalog history per publish — `listCatalogVersions`, `listWildcardDrift` | Drift answers `unsupported` |
| `AlfizMetric` | `metrics: {}` on the Application, `getGrantUsage` and the other usage reads | `createApplication` **throws** when `metrics` is set |

```prisma
/// The consumed-vocabulary manifest — catalog.toImportManifest().
model AlfizImports {
  id       Int  @id @default(1)
  version  Int
  manifest Json
}

/// The invalidation-log head — a singleton (always id = 1). One tiny indexed
/// read answers "did anything change anywhere?", which is the cross-process
/// cache-freshness signal behind `revalidateAfterMs`.
model AlfizEpoch {
  id            Int    @id @default(1)
  seq           BigInt
  prunedThrough BigInt @default(0)
}

/// Persisted invalidation events, contiguous by `seq` — the same events the
/// in-process stream carries, durable so other processes can replay them.
model AlfizEvent {
  seq     BigInt @id
  type    String
  payload Json
  at      BigInt

  @@index([at])
}

/// Rolling permission-usage counters: one row per counter per time bucket
/// (daily by default), keyed by grant id, revoke id, role id, permission
/// key, or scope type. Counters accumulate across app servers. Nothing here
/// is access data — dropping the table loses metrics and changes no decision.
model AlfizMetric {
  bucket    BigInt
  dimension String
  subject   String
  metric    String
  count     BigInt

  @@id([bucket, dimension, subject, metric])
  @@index([dimension, subject])
  @@index([bucket])
}
```

## `mongoDriver`

The MongoDB driver is the production driver shipped in `@alfiz/mongo`. It implements the `StorageDriver` interface directly over the official [`mongodb`](https://www.npmjs.com/package/mongodb) driver — no schema fragment to merge, no code generation step, and no migration. Point it at a database and go.

### Installation

```bash
npm install @alfiz/mongo mongodb
```

`mongodb` is a peer dependency (`^6.0.0 || ^7.0.0`). `@alfiz/mongo` does not depend on it directly.

### Creating a Mongo driver

```ts
import { MongoClient } from "mongodb";
import { createApplication } from "@alfiz/application";
import { mongoDriver } from "@alfiz/mongo";

const client = new MongoClient(process.env.MONGO_URL!);
await client.connect();

const storage = mongoDriver(client.db("alfiz"));
const app = createApplication({ catalog, storage /* ... */ });
```

`mongoDriver` also accepts a `Promise<Db>`, so you can construct the Application before `client.connect()` resolves:

```ts
const storage = mongoDriver(client.connect().then((c) => c.db("alfiz")));
```

Collections (`grants`, `revokes`, `roles`, `groups`, `users`, `requests`, `catalog`, `audit`, `epoch`, `events`, `locks`) and their hot-path indexes are created lazily on first use. Every row is stored with its Alfiz id as Mongo's `_id`, giving free uniqueness and point reads.

### `MongoDriverOptions`

`mongoDriver` accepts an optional second argument:

<ParamField body="leaseMs" type="number" default="10000" optional>
  Duration in milliseconds of the cross-process lease that `runExclusive` acquires in the `locks` collection. In a single-process deployment the in-process promise-chain mutex is sufficient. In a **multi-node deployment**, `runExclusive` also writes a best-effort lease so two nodes writing group parentage at the same moment cannot jointly form a cycle. An expired lease is stolen, so a crashed holder cannot wedge writes forever.

  ```ts
  const storage = mongoDriver(db, { leaseMs: 5_000 });
  ```
</ParamField>

### Persisted events, built in

The `epoch` and `events` collections back the Application's `events: { persist: true }` option out of the box — unlike the Prisma driver, no additive models to merge and no migration to run. Under the 0.7.0 auto default, `events` persistence turns on because the driver reports itself as capable.

### What this driver does not implement

Two optional method groups are absent:

| Missing methods | Effect |
|---|---|
| `getCatalogVersion`, `listCatalogVersions` | Catalog history is not retained. The [wildcard-drift report](/operations/access-reviews#wildcard-drift-what-changed-since-you-certified) answers `unsupported` rather than wrongly. |
| `recordMetrics`, `readMetrics`, `pruneMetrics` | `createApplication` **throws** when `metrics: {}` is set. |

Both groups are optional on `StorageDriver`. If you need either, use `prismaDriver` or implement the missing methods in a wrapper.

### Query safety

Nothing upstream of a storage driver validates the *runtime* type of an id or filter value — `@alfiz/application`'s Provider API checks field **presence**, not shape, so a JSON body carrying `{ "subject": { "$ne": null } }` reaches the driver unmolested. Every value `mongoDriver` assigns into a Mongo query document (an id, or a filter field such as `subject`, `scope`, `roleId`, `actor`) is checked to be the expected primitive first and rejected with a `TypeError` otherwise. An object-shaped value can never be read as a query operator instead of data.

## Multi-node deployments

The default in-process mutex inside the memory and Prisma drivers only serializes within one Node.js process. When you run multiple application instances against the same database, two concurrent group-parentage or reporting-edge writes could each pass their individual cycle checks while jointly forming a cycle. Supply the `lock` option to `prismaDriver` with a database advisory lock to prevent this. `mongoDriver` handles this on your behalf via the `locks` collection lease — tune the timeout with [`leaseMs`](#mongodriveroptions).

## Implementing a custom driver

If you use a database that neither `prismaDriver` nor `mongoDriver` covers — DynamoDB, a raw SQL driver, or similar — implement `StorageDriver` directly. The interface is in `@alfiz/application`:

```ts
import type { StorageDriver } from "@alfiz/application";

export function myCustomDriver(): StorageDriver {
  return {
    async insertGrant(row) { /* ... */ },
    async deleteGrant(id) { /* ... */ },
    // ... all other methods
    async runExclusive(key, fn) { /* advisory lock or mutex */ },
  };
}
```

Conventions a custom driver has to get right — and since 0.7.0, a published conformance suite that checks them for you:

```ts
// my-driver.test.ts — the whole file
import { test } from "vitest"; // or any runner; the cases use node:assert
import {
  driverContractCases,
  eventLogContractCases,
  metricsContractCases,
} from "@alfiz/application/driver-suite";

for (const c of driverContractCases) test(c.name, () => c.run(makeDriver()));
```

The suite covers the row round-trips, the audit ordering and filters below, catalog history, and — the case that matters most for correctness — **`runExclusive` serialization**, which is what keeps graph-cycle detection sound under concurrency. A driver that fails it is unsound multi-node, not merely non-conforming.

The conventions the suite pins:

- **Absent rows return `null`** — not `undefined`, and never a thrown error. Both bundled drivers follow this.
- **Audit order is (`at`, then `id`)**, and `listAudit({ limit })` returns the NEWEST `limit` events in that order, not the oldest — while `listAudit({ cursor })` returns the first `limit` strictly *after* the cursor, ascending, for export paging. The memory driver slices from the end; the Prisma driver orders ascending and takes `-limit`.
- **Catalog history is optional but honest**: implement `getCatalogVersion`/`listCatalogVersions` (and retain a row per `putCatalog`) to enable the [wildcard-drift report](/operations/access-reviews#wildcard-drift-what-changed-since-you-certified); omit them and the report answers `unsupported` rather than wrongly.
